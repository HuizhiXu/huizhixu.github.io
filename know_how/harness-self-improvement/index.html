RSI 笔记02｜Harness如何实现自我进化？

BY Sophia/ 2026年07月19日 /技术/8 分钟

如果你关注 AI 前沿技术，最近一定频繁看到一个词：RSI（Recursive Self-Improvement，递归自我改进） 。

那么，RSI 到底是什么？Harness 又是如何实现自我进化的？通过 Lilien Weng 的博客文章，我们可以知道最新的发展。

一、RSI：从“优化答案”到“优化获取答案的机制”

先来理解 RSI 的核心思想。

想象一下这个场景：

  • 传统做法：你让 AI 解一道数学题，AI 给出答案。如果答案不对，你调整 Prompt，再试一次。这是人在优化答案。
  • 更进一步：你让 AI 自己检查答案对不对，如果不对，于是它自己重新算一遍。这是 AI 在优化答案。
  • RSI 的做法：AI 不优化当前这道题的答案，而是去优化如何解题的这个流程——比如套用公式、优化调用计算器的逻辑、甚至重写整个任务拆分的策略。这是 AI 在优化“根据什么机制来生成答案”里的机制。

例如，AI 发现每次都要手动调用计算器很麻烦，于是它修改了自己的 Harness 代码，加了一个“遇到数学问题自动调用计算器”的规则。下次再遇到数学题，它不需要思考是否使用工具，Harness 已经写好了使用工具，那相当于它在原来的基础上进行了一次进化。

Weng 在文章中用了一个非常精炼的定义：RSI 是指人工智能利用自身当前的智能，去改进产生其智能的认知机制。

RSI refers to the fact that an AI uses its current intelligence to improve the cognitive machinery that produces its intelligence.

二、为什么 RSI 的第一步是改 Harness，而不是改模型？

我们一直在讨论 AI 智能，但所有人都希望是 AI 本身具有智能，而不是给大模型搭一个系统，让它看起来智能。

那按理来说，让 AI 直接去更新自己的模型权重，不是更彻底的自我进化吗？但是目前大家不会直接根据外界的反馈来直接更新模型的权重。

因为大模型的训练是一个极其昂贵且复杂的过程。让 AI 在运行时直接修改自己的权重，目前面临几个硬约束：

  1. 安全风险：一次错误的权重更新可能导致整个模型崩塌。
  2. 计算成本：即便是微调，也需要大量的GPU资源和时间。
  3. 评估困难：如何快速判断一次权重更新是变好了还是变坏了？

相比之下，修改 Harness 代码要简单、安全、高效得多。

上篇文章说过，Harness 本质上是一段代码——Python 脚本、配置文件、提示词模板。代码可以被阅读、被修改、被测试。

所以，当前 RSI 的主流路径是：让 AI 改进包裹自己的那层脚手架代码（也就是 Harness），而不是直接改造模型权重。

三、Harness自进化的几种方式

Lilian Weng 的文章详细介绍了 Harness 实现自我进化的几种方式。

机制一：Self-Taught Optimizer —— 改进“改进器”本身

这个机制的名字很有意思：自我教导的优化器。

它的核心逻辑是：

  1. 在初始时刻，有一个“种子改进器”I₀。它接收当前解s、效用函数u和模型M，输出一个改进后的解s'。
  2. 引入元效用（Meta-utility） 的概念。所谓元效用，简单说就是：“改进器”本身好不好，不取决于它把某一道题解得多好，而取决于它在一大批不同任务上的平均表现。
  3. 基于上一代改进器的元效用表现，递归地更新出下一代改进器。

也就是说：系统改进的不是当前任务的解，而是“改进器”本身。

在这个过程中，模型会自发涌现出高级搜索策略——比如遗传算法、模拟退火、束搜索等——这些策略并不是被显式编程进去的，而是模型在递归自我改进中发现的。

机制二：Self-Harness —— “提案-评估-接受”的进化循环

这是 Harness 自进化最直接的实现方式。整个流程可以概括为三步：

第一步：提案（Propose）

系统首先用当前的 Harness 执行任务，收集完整的执行轨迹。然后系统会：

  • 深层归因：同样的错误（比如“超时”）背后可能有完全不同的原因。系统需要收集大量的失败记录，这些记录包含验证层直接原因、智能体行为的因果状态、以及轨迹暴露出的抽象机制等内容。
  • 聚类模式：将这些失败案例聚类成有验证依据的失败模式。

接着，由同一个大模型充当“提议者（Proposer）”，在严格限定的上下文中提出修改方案。提议者能看到的信息被严格限制在四类：

  • 当前 Harness 可编辑的部分
  • 挖掘出的失败模式
  • 必须保留的正确行为记录
  • 之前尝试过的修改摘要

第二步：评估（Evaluate）

候选修改方案必须在训练集（验证问题是否被解决）和测试集（检查是否引入了未知的新问题）上同时通过测试。

第三步：接受（Accept）

只有在两个数据集上都没有出现性能回退（No regression）的方案才会被接受并合并为新版本的 Harness。被拒绝的方案只做记录，不会破坏现有系统。

机制三：进化搜索（Evolutionary Search）

这是目前 Harness 自进化中最引人注目的方向。

进化搜索的思想很简单：把 Harness 的改进看作一个生物进化过程。

  • 变异：系统生成多个不同版本的 Harness（比如修改提示词、调整工具调用逻辑、重构控制流）。
  • 选择：评估每个版本的性能（在真实任务上打分）。
  • 遗传：保留表现最好的版本，在此基础上继续迭代。

这个思路之所以有效，是因为：Harness 的搜索空间极其庞大且形状怪异，很难用传统的梯度下降直接优化，但很容易对结果进行评估打分。 这正好契合了进化搜索的优势。

Weng 在文章中提到了两个代表性案例：

  1. Darwin Gödel Machine (DGM)

DGM 允许一个基于 LLM 的编程智能体通过 bash 和 editor 工具直接查看自己的评估日志，并修改自己的 Harness 代码库来生成新版本。系统会根据性能挑选父代进行分支变异，只有性能足够高的新智能体才会被放回池中。

结果相当惊人：在底层模型（Claude 3.5 Sonnet）权重不变的情况下，DGM 进化出的智能体在 SWE-bench 和 Polyglot 等测试中，大幅超越或媲美了人类手工设计的智能体。

这意味着同一个模型，仅仅因为包裹它的工程代码被优化了，就能在复杂任务上表现出截然不同的能力。

  1. AlphaEvolve

另一个典型的进化搜索框架。它同样通过“生成→评估→筛选”的循环来优化智能体系统。

机制四：Meta-Harness —— 从优化上下文到优化完整程序

虽然在原博客文章中，这一章被写在上下文工程，但是我觉得它从理念上更属于 Harness 的全局代码更改，所以放在这里。 如果说 ACE 优化的是“上下文内容”，MCE 优化的是“上下文管理技能”，那么 Meta-Harness 把优化目标拓展到了整个Harness程序。

Meta-Harness 的核心特征是：

1. 一切皆为代码

没有“技能”这个概念了——优化目标不再是提示词或上下文，而是 Harness 程序本身。程序直接生成不同版本的代码，然后选择最优。

2. 多目标优化

Meta-Harness 在搜索时，同时考量多个相互冲突的目标，最典型的是“任务准确率”与“上下文开销”（也就是 Token 消耗/成本）。

3. 基于“支配关系”的筛选

根据帕累托最优法则，如果 Harness A 在准确率上优于 Harness B，且上下文开销不高于 B，则称 A“支配”B。那些没有被任何其他方案在所有目标上同时超越的方案，被称为“非支配解”——这些就是最优候选。

4. 全量历史文件系统访问

整个执行历史都通过文件系统暴露给智能体。智能体通过 grep 或 cat 等命令自主查阅旧代码、分数和执行轨迹，而不是把所有信息硬塞进单一的提示词上下文里。

四、RSI 的本质，不是学习，而是搜索

读完博客文章的自我进化那一节时，我有种感觉：Harness 的自进化，本质上是一个搜索问题，而不是学习问题。

两者的区别在于：

  • 学习：给定数据，调整参数，拟合规律。
  • 搜索：在庞大的可能性空间中，找到那个最优的 Harness 方案。

无论是 Self-Harness 的“提案-评估-接受”循环，进化搜索的“变异-选择-遗传”机制，还是 Meta-Harness 的帕累托优化——它们本质上都在做同一件事：搜索。

所以，RSI 的实际运作方式，就是AI在不断尝试新的 Harness 配置，评估表现，保留好的，抛弃差的。

这不就是工程优化的本质吗？只不过以前是人在做这一步，现在AI让这个过程变得更快、更系统化。

五、自进化的边界：为什么模型智能依然重要？

前段时间 Openclaw 很火的时候，我发现好多人都想用小模型，特别是那种自己能在本地部署一个 10B 以下的模型的人，希望将 Openclaw 连到本地小模型来使用。后来连上了他们发现，为什么我的吐字这么慢？为什么它不思考？为什么它不调用工具？

同样，在讨论 Harness 自进化时，我们也很容易陷入一个误区：觉得只要 Agent 或者 Harness 这个框架足够好，模型本身差点也没关系。

Lilian Weng 的文章给出了一个重要的提醒：同一个 Harness 在不同的大模型下使用效果是不一样的。

她引用了研究中的两个关键发现：

发现一：生成有效 Harness 的能力，在不同量级的模型间差异不大。

研究发现，像 Qwen3.5-9B 这样的小模型作为“提议者”，写出的技能在程序结构上与顶级的 Claude Opus 4.6 几乎相同。

发现二：利用更新后的 Harness 来执行任务的能力，严重依赖模型本身的能力。

优秀的执行能力代表着模型必须具备以下能力：

  • 正确且及时地调用工具/技能
  • 优秀的长程指令遵循（long-horizon instruction following）能力

这就形成了一个有趣的分工：小模型负责出方案，大模型负责干活。

说实话，这和我平时用 Cursor 的习惯完全相反——我习惯用 Sonnet 出方案、让 Composer 执行。看到这个结论时我愣了一下，难道我一直用反了？这个还有待确认。

六、预告与思考

在这一篇里，我们讨论了：

  1. RSI 的核心思想：从“优化答案”到“优化获取答案的机制”
  2. 为什么先改 Harness 而不是改权重：更安全、更高效
  3. Harness 自进化的机制： Self-Taught Optimizer、Self-Harness、进化搜索、Meta-Harness
  4. 搜索 vs 学习的本质区分：Harness 自进化是搜索问题
  5. 模型智能依然重要：小模型负责搜索，大模型负责执行

Lilian Weng的博客提供了一个很好的技术视角，但它不是 RSI 讨论的全部。关于 RSI，业界还有很多不同的声音。除了这篇博客，我也做了一些其他的调研。

第三篇，我想换个视角，不再局限于这一篇博客，而是结合我看到的其他讨论，聊聊业界的争议与分歧。
